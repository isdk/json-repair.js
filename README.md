# @isdk/json-repair

> 【English|[中文](./README.cn.md)】

A powerful, schema-guided JSON repair library specifically designed to fix "broken" JSON generated by LLMs (Large Language Models).

[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](https://opensource.org/licenses/MIT)
[![npm version](https://badge.fury.io/js/@isdk%2Fjson-repair.svg)](https://www.npmjs.com/package/@isdk/json-repair)

## 🚀 Why this library?

LLMs often output JSON that is syntactically invalid or semantically "noisy". Common issues include:

- Missing quotes around keys or values.
- Unescaped quotes inside strings (e.g., `"a"b"`).
- Missing commas or closing braces.
- Natural language mixed into values (e.g., `"age": "about 30 years old"`).
- Implicit structures (e.g., an array of objects without curly braces).

Standard `json-repair` libraries only fix syntax. **@isdk/json-repair** uses your **JSON Schema** as a map to intelligently navigate, repair, and coerce the output into valid, structured data.

## ✨ Key Features

- **Schema-Guided Repair**: Uses your Schema to resolve ambiguities (e.g., knowing if a colon marks a new key or is part of a string).
- **Greedy String Capture**: Intelligently captures unquoted or broken strings until the next valid Schema key.
- **Balanced Delimiter Tracking**: Correctly handles structural markers (commas, colons) inside parentheses, brackets, or braces within DSL-like strings (e.g., `@func(a, b)`).
- **The "Parity Rule"**: Solves nested quote ambiguity (e.g., correctly distinguishing between `"A" OR "B"` and `"a"b"`).
- **Semantic Coercion**:
  - **Fuzzy Enum Matching**: Matches "Processing!" to `"processing"` if defined in Schema enums.
  - **Noisy Number Extraction**: Extracts `1200.5` from `"Approx. 1,200.50 USD"`.
  - **Boolean Variants**: Recognizes `yes/no`, `on/off`, `1/0`, `确定/取消` as booleans.
- **Implicit Structure Support**: Automatically repairs missing braces in objects and arrays.
- **Robust Property Boundaries**: quoted keys may contain spaces and punctuation (`"Official language": "Italian"`); a value that parses cleanly is never re-tokenized, so valid JSON round-trips exactly like `JSON.parse`.
- **Fuzzy Key Matching**: `user_name`, `userName` and `USER NAME` resolve to the property your Schema declares, and the output carries the declared name.
- **Prototype-Safe Output**: keys such as `__proto__` or `constructor` are stored as own data properties, exactly as `JSON.parse` leaves them.
- **Performance**: Support for reusing `SchemaWalker` instances for high-throughput batch processing.

## 🛠 Usage

### 1. Schema-Guided Repair (Recommended)

This is the most powerful way to use the library. Providing a schema enables advanced features like semantic coercion, greedy capture, and accurate disambiguation.

```typescript
import { jsonRepair } from '@isdk/json-repair'

const schema = {
  type: 'object',
  properties: {
    query: { type: 'string' },
    status: { enum: ['success', 'error'] },
  },
}

const brokenJson = '{ query: "python" OR "js", status: Success! }'

const result = await jsonRepair(brokenJson, schema)
console.log(result)
// Output: { query: '"python" OR "js"', status: 'success' }
```

### 2. Simple Usage (Without Schema)

For basic syntax repair where schema guidance isn't required:

```typescript
import { jsonRepair } from '@isdk/json-repair'

const result = await jsonRepair('{ name: John, age: 30 }')
console.log(result) // { name: 'John', age: 30 }

// Quoted keys may contain spaces and punctuation; valid JSON round-trips untouched.
const country = await jsonRepair(
  '{ "Capital": "Berlin", "Official language": "Italian" }'
)
console.log(country) // { Capital: 'Berlin', 'Official language': 'Italian' }
```

### Advanced: Reusing SchemaWalker (Batch Processing)

For better performance when processing many items with the same schema:

```typescript
import { jsonRepair, SchemaWalker } from '@isdk/json-repair'

// Options that concern the Schema itself (`keyMatching`) belong to the walker.
const walker = await SchemaWalker.create(mySchema, { keyMatching: true })

for (const item of brokenItems) {
  const result = await jsonRepair(item, walker)
  // ...
}
```

## 🧭 How Property Boundaries Are Detected

While repairing a value, the parser must decide at every position whether an upcoming
`"foo":` starts the **next property** or is just part of the **current value**. It uses two modes:

1. **Structural mode** — applies right after a value was parsed by the strict JSON path
   (a balanced `"string"`, a well-formed number, `true`/`false`/`null`).
   Any key-shaped token followed by `:` counts as the next property, _including quoted keys
   that contain whitespace or punctuation_ (`"Official language":`, `"a, b":`, `"a: b":`).
   A successful strict parse is **never** discarded, which is why valid JSON always yields
   exactly what `JSON.parse` would return.
2. **Greedy mode** — applies when the value could not be parsed strictly (unquoted text,
   unescaped inner quotes, `"A" OR "B"` expressions, DSL snippets such as `@func(a="x, y")`).
   - If the Schema declares property names for the current level, capture stops **only at a
     declared key**. Text that merely looks like a key stays inside the value:
     `{ "query": he said "hello there": loudly, "intent": "x" }` keeps
     `query = 'he said "hello there": loudly'`.
   - If the Schema declares no property names for that level (no schema, `type: "object"`
     without `properties`, or only `additionalProperties`), the parser falls back to
     “the first key-shaped token ends the value”.

   Set `stringCaptureStrategy: 'conservative'` to make greedy mode stop at _any_ key-shaped
   token, whatever the Schema declares (see [Repair Options](#-repair-options)).

### Thinking about the heuristic

Ambiguity is missing information, not magic: `{ "note": see "foo bar": baz here, "b": 2 }`
cannot be decided without a schema, because both readings are plausible. The principles the
parser follows are:

- A **cleanly parsed** value is trusted; whatever follows it is assumed to be structure.
- A **messy** value is preserved as text whenever the Schema can name the real anchors.
- Consequently, **declaring the `properties` of the current level is the single most effective
  way to steer the repair** — declared keys act as breakpoints for greedy capture, and
  declared `type`/`enum` enable semantic coercion.
- If a value may legitimately contain `word:` or `"phrase":`, prefer having the model emit
  properly escaped JSON (then the strict parse wins outright), or declare that level's
  properties in the Schema.
- If a value looks truncated right at something key-shaped, that level is probably missing
  `properties` in your Schema — add them and re-run.

Numeric literals support scientific notation (`1e5`, `-2E2`) as well as the lax LLM forms
`+5`, `.5` and `5.`. A partial literal such as `1.2.3` is kept as a string and then coerced
according to the Schema.

## ⚠️ Known Limitations & Disambiguation

- **The "Parity Rule"**: When a string is wrapped in quotes and contains internal quotes, we count the internal ones.
  - Odd count (e.g., `"a"b"`): We assume the outer quotes are delimiters -> `a"b`.
  - Even count (e.g., `"A" OR "B"`): We assume the outer quotes are part of the expression -> `"A" OR "B"`.
  - **Limitation**: Highly unusual patterns like `"a"b"c"` might remain ambiguous.
- **Key-shaped text inside a broken value (no schema guidance)**: when the Schema declares no property names for the current level, the first key-shaped token ends the value.
  `{ "note": see "foo bar": baz here, "b": 2 }` without a schema is therefore read as `{ note: 'see', 'foo bar': 'baz here', b: 2 }`. Declaring that level's `properties` makes greedy capture stop only at real keys and restores `{ note: 'see "foo bar": baz here', b: 2 }` (see [Thinking about the heuristic](#thinking-about-the-heuristic)).
- **Markdown Blocks**: This library focuses on the JSON content. Please strip `json ...` markers before passing the string if your LLM includes them.

## ⚙️ Repair Options

`jsonRepair(input, schema, options)` takes a fourth argument of type `RepairOptions`:

| Option                  | Default        | What it does                                                                                                                                                                                                                                                                                                                                                     |
| ----------------------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `coerceTypes`           | `true`         | Converts a value to the type the Schema declares: `"Approx. 1,200.50 USD"` → `1200.5`, `"yes"` → `true`, `"Processing!"` → `"processing"` when the enum says so.                                                                                                                                                                                                 |
| `keyMatching`           | `false`        | Resolves incoming keys to the names the Schema declares. `true` ignores case and separators, so `user_name`, `userName` and `USER NAME` all match `userName`; a function `(key, properties) => string \| undefined` decides itself (`undefined` keeps the key as it is). A match renames the key in the output, which also re-enables coercion for that subtree. |
| `additionalProperties`  | `'keep'`       | `'remove'` drops keys the Schema does not declare. Applied only at levels that do declare `properties` — a free-form level has no “extra” keys and is left untouched. Independent of the JSON Schema keyword `additionalProperties: false`, which is honoured on its own.                                                                                        |
| `stringCaptureStrategy` | `'aggressive'` | `'conservative'` ends greedy capture at any key-shaped token instead of only at declared Schema keys: less risk of one broken value swallowing the rest of the document, at the cost of cutting values short.                                                                                                                                                    |

```typescript
const schema = {
  type: 'object',
  properties: {
    userName: { type: 'string' },
    userAge: { type: 'number' },
  },
}

await jsonRepair('{ user_name: "Ada", user_age: "36" }', schema, {
  keyMatching: true,
  coerceTypes: true,
})
// { userName: 'Ada', userAge: 36 }

await jsonRepair('{ userName: "Ada", reasoning: "let me think…" }', schema, {
  additionalProperties: 'remove',
})
// { userName: 'Ada' }

const querySchema = {
  type: 'object',
  properties: { query: { type: 'string' }, intent: { type: 'string' } },
}

await jsonRepair(
  '{ "query": he said "hello there": loudly, "intent": "x" }',
  querySchema,
  { stringCaptureStrategy: 'conservative' }
)
// { query: 'he said', 'hello there': 'loudly', intent: 'x' }
```

`keyMatching` is read from the options passed to `SchemaWalker.create()` when you reuse a
walker; the other options are read on every `jsonRepair()` call.
